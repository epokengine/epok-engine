# Lua feasibility harness (native AOT reference vs. PsyQo Lua VM)

This directory holds an **isolated PsyQo benchmark harness**. It is not the Epok
renderer, not the editor, and not a game. It links **no Epok engine code at
all** — not even `runtime/blueprint_runtime.hpp` — so that the numbers it
produces describe the scripting technologies rather than the engine around
them.

It exists to satisfy the "Benchmark needed before choosing the implementation"
section of the Lua execution-options comparison that preceded this implementation,
which required a matched-workload runtime benchmark before Epok commits to
either a typed AOT gameplay compiler or a PsyQo Lua VM integration.

Driver: [`../verify_lua_feasibility.py`](../verify_lua_feasibility.py).

## The four variants

| Variant | Lua archive | Chunk source | Dispatch |
| --- | --- | --- | --- |
| `native` | none | none | per-instance handler pointer, direct field access, no heap |
| `vm-parser` | `liblua.a` | Lua source, loaded once before timing | instance table field lookup, then `lua_pcall` |
| `vm-noparser` | `liblua-noparser.a` | precompiled bytecode | identical to `vm-parser` |
| `vm-cached-dispatch` | `liblua-noparser.a` | the same precompiled bytecode | event bitmask test, then numeric-id registry lookup, then `lua_pcall`; chunk re-loaded per instance for state isolation |

`vm-parser` and `vm-noparser` differ **only** in which archive they link and
whether the chunk arrives as source or as bytecode. Bindings, instance layout,
dispatch, numeric behaviour, optimisation flags and simulation steps are the
same lines of code. That isolates parser removal instead of conflating it with
integration choices.

`vm-cached-dispatch` adapts two integration choices a prior PsyQo Lua integration
documents — cached event functions under numeric registry ids with an event
bitmask checked before entering Lua, and per-object state isolation by
re-loading the chunk per instance. **No third-party integration code was copied**; only the
ideas are reimplemented here against the same pinned `psxlua` core.

## Files

| File | Role |
| --- | --- |
| `q12.hpp` | self-contained mirror of `runtime/blueprint_runtime.hpp`'s `epok::bp` numerics (Q12 raw `int32`, `4096 == 1.0`, saturating `int64` intermediates, divide-by-zero to zero). If that engine header changes, this file must be updated by hand and the harness re-run. |
| `harness.hpp` | probe layout, marker ids, workload/instance tables, the 60 Hz step clock, the checksum fold |
| `harness_common.cpp` | probe storage, the three breakpoint markers, stack-band painting |
| `native_main.cpp` | variant 1 |
| `vm_main.cpp` | variants 2, 3 and 4, selected by `-DHARNESS_VARIANT=` |
| `workloads_lua.hpp` | the seven Lua chunks |
| `harness_dump.c` | calls the internal `luaU_dump(..., strip=1)`, because Lua 5.2's public `lua_dump()` has no strip parameter; compiled into `vm-parser` only |

## Workloads

Seven workloads, each run at 1, 16, 32 and 64 instances, in all four variants.

| Workload | Per step, per instance |
| --- | --- |
| `absent` | no update handler exists at all |
| `empty` | handler present, empty body |
| `arith` | Q12 multiply/add plus an integer branch |
| `native_call` | one call into a native scalar method |
| `position` | get a 3-component position, modify it, set it back |
| `alloc` | allocation-heavy transient per-step state |
| `event_only` | no update handler; a discrete event fires every 16th step |

Each case runs 6 warm-up steps and then 60 measured steps. The simulation clock
is Epok's: 60 Hz, Q12 seconds, raw deltas alternating 68/69 without cumulative
drift, generated by native code copied from `runtime/time.hpp`
`Time::begin_tick()` and therefore identical in every variant.

## Correctness gate

Every workload folds its final per-instance state (`v`, `n`, `px`, `py`, `pz`)
through the same FNV-style checksum, written to an observable probe array in
guest RAM. The driver asserts that all four variants produce the **same
checksum and the same handler-call count** for every one of the 28 cases. A
mismatch is reported as a harness correctness failure and makes the run exit
non-zero; it is never smoothed over.

The checksum is also what prevents dead-code elimination: the native variant
cannot have its arithmetic removed, because the result leaves the program.

### A caveat the checksum does not remove

`lua_Number` in this `psxlua` fork is `long`, i.e. a 32-bit integer on MIPS
o32, so Lua arithmetic **wraps** at 32 bits while `epok::bp` **saturates** using
`int64` intermediates. Every expression in `workloads_lua.hpp` is deliberately
bounded so the two agree bit for bit. That is a property of these specific
workloads, not a general equivalence. A real Epok Lua integration would have to
route Q12 arithmetic through bindings (or accept different overflow semantics).

Likewise, the Lua chunks operate on **raw Q12 integers**, not on psyqo
`FixedPoint` tables. The `position` binding builds one fresh three-component
table per call, but its components are plain numbers, not a `FixedPoint` table
each. The 268-byte-per-position figure estimated in
The pre-implementation comparison describes the `FixedPoint` table representation; this
harness measures the cheaper one, and its allocation numbers are therefore a
**lower bound** for a `FixedPoint`-based binding.

## Bytecode ABI

A desktop `luac` is not assumed to produce valid PSX bytecode, and on this
machine it cannot even be built (`make host32` in the pinned `psxlua` fails at
link time on macOS arm64 — recorded in the report under
`bytecode_abi.host_luac`).

Instead the harness cooks the bytecode **on
target**: the `vm-parser` executable runs under headless PCSX-Redux, compiles
each chunk with the target Lua, dumps it with `luaU_dump(..., strip=1)` into a
guest buffer, and the PCSX-Redux driver script reads that buffer back out of
guest RAM. The bytes are then embedded into the two no-parser builds as a
generated `bytecode_blob.h`.

The ABI check is explicit rather than assumed:

* Each build calls the linked `luaU_header()` and writes the 18 header bytes it
  will accept into the probe. The report decodes them (signature, version,
  format, endianness, `sizeof(int/size_t/Instruction/lua_Number)`, integral
  flag, `LUAC_TAIL`) and records the raw bytes.
* The driver checks that every dumped chunk begins with exactly that header,
  and that the chunk sizes sum to the blob size.
* If a no-parser build rejects a chunk, `harness_probe[LOAD_OK]` goes to zero,
  the emulator log carries the Lua error, and the run fails. That would be
  reported as a finding, not patched around.

## Reproducing

Prerequisites: `mipsel-none-elf-gcc/g++/size/nm/ar` on `PATH`, the pinned
`third_party/nugget` submodule checked out (which carries `psyqo`, `psyqo-lua`
and `third_party/psxlua`), PCSX-Redux under `.tools/`, and Python 3.

```sh
# build + linked sizes only (still needs the emulator to cook bytecode)
python3 tests/integration/verify_lua_feasibility.py --output report.json

# build + guest-cycle measurement
python3 tests/integration/verify_lua_feasibility.py --emulator \
    --build-dir /tmp/epok-lua-feasibility --output report.json
```

The driver **copies** the pinned Nugget tree into the build directory before
building, so nothing in the repository is written to. `liblua.a` and
`liblua-noparser.a` share object files in the upstream Makefile, so they are
built one after another with an intervening `make clean` and copied out. All
four executables are built `BUILD=Release` (`-Os`), with identical flags.

Runs are deterministic: fixed step count, fixed delta sequence, fixed instance
counts, no input, no wall-clock dependence.

## What the numbers mean, and what they do not

**Measured by this harness**

* Guest CPU cycles between identical `harness_mark_begin` / `harness_mark_end`
  markers, reported as min / median / p95 / max / sum over the 60-step window,
  per variant and per (workload, instance count).
* Setup, chunk-load, VM-open and teardown cycles, reported separately from
  steady state.
* `.text` / `.rodata` / `.data` / `.bss` of the **linked executable**, from
  `mipsel-none-elf-size -A`.
* Lua heap: retained bytes, peak live bytes, allocation and free counts and
  total allocated bytes, taken from the harness's own `lua_Alloc`, which
  receives exact old and new sizes.
* Stack high water, from a painted 32 KiB band below the initial frame,
  discarded if the heap ever reached into the band.

**Not measured, and not claimed**

* Nothing here was validated on physical PlayStation hardware. Emulator cycle
  counts are for reproducible development comparison only.
* Guest cycles are not host time, not frame time and not FPS. No speedup
  multiplier or FPS figure is reported that this run did not measure.
* Archive (`.a`) sizes appear in the report only as archive sizes. They are not
  RAM consumption and not linked sizes.
* Heap figures cover Lua allocations only — not the psyqo allocator's own block
  headers, fragmentation, or the native side's stack and static data.
* The measured window includes the tail of the begin marker and the mark-id
  store. That offset is a constant and is identical in every variant, but it is
  not zero, so very cheap cases (`absent`, `empty` in `native`) are dominated by
  it.
* The harness runs one class at a time. The "many unique scripts" memory term
  from the pre-implementation comparison is not exercised; only repeated instances
  of one script are.
* There is no scene cycling and no memory-exhaustion test here.
